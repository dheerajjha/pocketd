Privacy Policy

Pocketd · Last updated 12 September 2026

Two kinds of request leave your phone: model searches and downloads, which go to Hugging Face, and a fixed list of usage events, which go to Mixpanel. Nothing else is sent anywhere. Your conversations, everything the model says back, and anything Pocketd reads from Health, Calendar or Reminders stay on the device and cannot appear in either kind of request.

The rest of this page is the detail behind those two sentences, including the parts that are less tidy than the sentences are.

What Pocketd collects about you

Usage events, and nothing besides. There are fifteen of them and the complete list is one readable file, AnalyticsEvent.swift: the app was opened; the intro was finished or skipped; a model download started, finished, was cancelled or failed; a model loaded or failed to load; a message was sent; the server started or stopped; a client on your Wi-Fi was answered; a request was refused because the phone was too hot, too low on battery, or already busy.

An event may carry a model's id, a file size in bytes, how long something took, a rounded memory class for the phone (4gb, 8gb, 16gb_plus), a reason drawn from a fixed list, and which of the two APIs a client spoke. Alongside those, the analytics SDK attaches an identifier for this installation of the app, the app version, the iOS version and the device model.

These events are sent from every installation. There is no switch that turns them off.

What an event cannot contain is not a matter of anyone's good intentions. The property names an event is permitted to use are written out by hand in AnalyticsSchema, next to a list of names that are banned outright — prompt, message, transcript, response, url, filename, address, api_key, steps, heart_rate, sleep, calendar, reminder and the rest — and a test in the repository fails the build if any event carries a banned name, or a name that appears on neither list.

What is still true, and is most of why the rest of this page is worth reading:

  • No account, no sign-in, no email address, no name.
  • Nothing you type, and nothing the model replies, is transmitted to anyone. Inference happens on the phone.
  • No crash reporting.
  • No advertising and no ad identifier. Pocketd does not link an advertising framework and never asks for permission to track. Usage events are not joined to anything you do in another app or on any website, and nothing is sold or handed to a data broker.
  • Three outside components, and only one of them reports anything: an HTTP server (FlyingFox), the inference runtime (LocalLLMClient, wrapping llama.cpp), and the analytics SDK (Mixpanel), which sends the events above and nothing else.

The app's PrivacyInfo.xcprivacy says the same thing to Apple: tracking off, tracking domains empty, and two collected data types — Product Interaction and Device ID — both declared not linked to your identity, not used for tracking, and collected for analytics.

What leaves your phone

Two hosts. huggingface.co, with the CDN it redirects downloads to, for models; and api.mixpanel.com, for the usage events above. Only these things cause a request:

WhenWhat is sent
You search for a modelThe text you typed, as a search term, and your phone's IP address
You open a repository to see its filesThe repository's name, and your phone's IP address
You download a modelWhich repository and file you are fetching, and your phone's IP address
You use the appOne of the fifteen usage events, the identifier for this installation, and your phone's IP address

A paired device on your network can ask the phone to run a search or start a download on its behalf, which sends the same things and nothing more.

Neither an account nor a token is attached to any of them, because Pocketd has neither to attach. The identifier in the last row is one the analytics SDK generates for the installation; it is not the advertising identifier and it is attached to nothing but those fifteen events. Every download address is assembled as huggingface.co, then a repository and a filename; the search API accepts a repository and a filename and never a host. The stored record for a model carries a field that could name a different address, and nothing in the app or its HTTP API ever sets it.

Nothing else is contacted. Inference does not call out — the weights are a file on your phone, and answering a question reads that file. The web pages Pocketd serves are self-contained, with no fonts, scripts or images loaded from anywhere.

Health, Calendar and Reminders

If you grant access, the assistant can answer questions about your activity, heart and sleep, your calendar and your reminders.

  • The data is read on this device and is never uploaded. It goes to a file of weights on your phone and comes back as an answer.
  • Network callers cannot reach it. Pocketd serves other devices on your network, and those devices are refused this data — including the chat page Pocketd itself serves, which is treated as a network client like any other. The decision is made from the connection's own peer address, before any read happens, so a refused request causes no read at all rather than a filtered one. Only someone holding the phone and using the Chat tab can get an answer containing personal data.
  • Health data is never used for advertising or marketing, never sold, and never disclosed to anyone. It cannot ride out in a usage event either: steps, heart_rate, sleep, workout, calendar, reminder and event_title are on the banned list a test enforces, and an event carrying a property name that is not explicitly permitted fails the build.
  • Pocketd never writes to Health. The write permission string exists only because iOS requires one from any app that links HealthKit.
  • Health data stays out of iCloud. Conversation transcripts are excluded from iCloud Backup, because an answer about your sleep or resting heart rate is saved in the transcript along with the rest of the conversation.

One thing Pocketd cannot tell you: iOS never reports to an app whether a request to read Health was allowed. That is deliberate on Apple's part — it stops an app distinguishing "you said no" from "you have no data of that kind" — and it applies to Pocketd like every other app. The app's own Data screen says so rather than guessing. Health → Data Access & Devices → Pocketd is the only place with the answer.

What is stored on your phone

Everything Pocketd keeps stays inside the app's own container:

  • Models you downloaded. Not about you.
  • Conversations — everything typed in the Chat tab and everything the model replied, as plain text, one file each.
  • Settings, including the API key other devices use to reach this phone.
  • Queued usage events, held by the analytics SDK until they are sent and deleted once they are.
  • Caches iOS keeps on the app's behalf, and snapshots iOS takes of the app when you switch away.

Models and conversations are both excluded from iCloud Backup. The Data screen inside the app walks the container and accounts for every byte, names what it cannot delete and says who can, and offers to delete the rest. Deleting the app removes all of it.

The local network

When you press Start, your phone runs an HTTP server for other devices on your Wi-Fi.

  • The server only answers. It accepts connections and never opens one.
  • While it is running, the phone announces itself over Bonjour to everyone on the same Wi-Fi: the device name iOS knows it by, the app version, which APIs it speaks, whether a key is required, and the id of the loaded model. That is how a laptop finds the phone without anyone typing an address. It does not leave the local network, and it stops when the server stops.
  • Requests can require a key, and pairing is a six-digit code shown on the phone. Anything reaching the server still cannot read your Health, Calendar or Reminders — see above.

The awkward parts

Worth saying plainly, because they are real and they are the kind of thing a privacy page usually leaves out:

  • The usage events are on by default. You are not asked during the intro; the intro tells you they exist and where the switch is. Settings has a Usage section that turns them off, and turning it off also discards anything queued and not yet sent. On-by-default is a real choice with a real cost — most people never change a default, so most installs will send these events. That is the point of them, and it is why the schema and the test that stand between them and anything you typed matter more than the switch does.
  • Opening a model's page hands the address to Safari. What Safari sends from that point is Safari's business, with Safari's cookies, not Pocketd's.
  • Copying the API key or the server address puts it on the system pasteboard. If Handoff is on, Universal Clipboard forwards the pasteboard to your other Apple devices through iCloud. That is an iOS feature and applies to anything you copy.
  • Hugging Face sees your IP address when you search or download, as any website does, and its CDN may set cookies that the system's HTTP client stores. The Data screen lists that cache and can delete it.

Children

Pocketd has no account, no sign-up and no social features, and asks nobody their age, because it has no reason to know it. The usage events above are sent from every installation and describe what the app did rather than who was holding it: no name, no email address, no age, no location, and nothing anyone typed.
